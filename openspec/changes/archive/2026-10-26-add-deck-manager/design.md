# Design

## Context

新規リポジトリで、既存コードは無い。動機は proposal.md の Why を参照。

- 公開先は GitHub Pages（静的配信のみ、サーバー側の処理は持てない）
- 主な利用端末はスマホ。カードショップの店頭で開くことを想定する
- 日本語のカード名と読み仮名を一括で取れるのは ygocdb の `cards.zip`（約2.4MB、14,343件、うち日本語名なし37件、種類の情報なし44件）。カードIDは公式カードデータベースの `cid` と同じ
- 禁止制限の状態は公式カードデータベースの一覧ページ（`forbidden_limited.action`）。サーバー側で描画された HTML で、`id="list_forbidden"` / `id="list_limited"` / `id="list_semi_limited"` / `id="list_release_of_restricted"` の区切りの間に各カードの `cid=` へのリンクが並ぶ。2026-10-25 時点で禁止94・制限95・準制限13。YGOPRODeck の `banlist_info.ban_ocg` と全件突き合わせたところ3枚が食い違っていた（公式で規制、YGOPRODeck で無制限）
- 種類の補完と切り抜きイラストは YGOPRODeck の `cardinfo.php?misc=yes`（`misc_info[0].konami_id` が公式の `cid`）。画像は直リンク禁止で、一度ダウンロードして自前で置くことを求めている
- 日本版の収録パック（型番）は YGOResources の `/data/card/<cid>` の `cardData.ja.prints`。CORS が許可されていて、画面から1枚ずつ取れる

## Goals / Non-Goals

**Goals:**

- ルール判定・並び順・検索・買い物リストの計算を、画面の部品から切り離した純粋な関数にし、Node だけでテストできるようにする
- 外部データの取得と変換は週1回のバッチに閉じ込め、画面からはリポジトリ内のファイルだけを読む（収録パックの取得だけは例外）

**Non-Goals:**

- アカウントやサーバー側への保存、端末間の自動同期
- カードラッシュの価格の自動取得
- ラッシュデュエル、海外専用カード、トークン

## Decisions

### 1. 構成: ビルド工程なしの静的サイト

`index.html` と ES modules を直接配信する。`src/core/` に DOM を触らない処理（判定・並び・検索・集計・保存形式の検証・復号）を置き、`src/ui/` に画面を置く。テストは `node --test` で `src/core/` を対象にする。

- 代替案: Vite 等でビルド → 依存と手順が増え、Pages への配信も一段増える。画面の規模に見合わないので採らない

### 2. カードデータの生成（Python、uv）

`tools/build_cards.py` が次を行い、`data/cards.json` と `data/meta.json` を書く。

1. `cards.zip.md5` と公式の禁止制限一覧を取る。一覧から区切りごとの `cid` を読み、どれかの区切りが見つからないか空なら失敗させる。`cid` と状態の組を並べたもののハッシュを作る
2. 更新判定値と一覧のハッシュが両方とも `data/meta.json` の値と同じなら何もせず終わる
3. `cards.zip` と YGOPRODeck の全カードを取り、`cid` で結び付ける。状態は一覧にあればその値、無ければ無制限
4. 日本語名の無いカードは除く。種類の情報が ygocdb に無いカードは YGOPRODeck の `frameType` で補い、どちらにも無ければ除いて `data/meta.json` の除外一覧に載せる
5. 種類のビット（YGOPro 形式: 0x10 通常, 0x20 効果, 0x40 融合, 0x80 儀式, 0x2000 シンクロ, 0x4000 トークン, 0x800000 エクシーズ, 0x1000000 ペンデュラム, 0x4000000 リンク, 0x2 魔法, 0x4 罠）から区分・表示グループ・枠の種類を決める
6. 1件を短い配列 `[cid, 名前, 読み, 表示グループ, 枠, 制限]` にして書く（約1.5MB、Pages が gzip で配る）

- 代替案: YGOResources の名前索引＋1枚ずつの取得 → 読み仮名を得るには全件を1枚ずつ取る必要があり、先方が控えるよう求めているので採らない

### 3. 検索

読み込み時に各カードの名前と読みを正規化して持つ。正規化は NFKC → カタカナをひらがなへ → 小文字化 → 文字と数字以外（空白・中黒・ダッシュ等）を除く。入力も同じ正規化をかけ、全件を線形に走査する（約14,000件で十分速い）。前方一致を先、その中は読みの順。

### 4. 利用者データの形

```json
{
  "version": 1,
  "decks": [
    { "id": "d1", "name": "リビングデッド", "cover": 12950,
      "entries": [ { "cid": 12950, "area": "main", "count": 3, "missing": 1, "seq": 4 } ] }
  ],
  "notes": { "12950": { "price": 580, "rarity": "SE", "print": "RC04-JP009" } },
  "nextSeq": 5
}
```

- 1つの `entries` 要素が「あるデッキのある区分（main / extra / cand）の、あるカード」。同名を隣に並べる要件は、カードごとに1要素にすることで自然に満たす
- `seq` は最初に追加した順番。並びは「表示グループの順 → seq」
- 未所持は `missing`（0〜count）。抜くときは `missing` から先に減らす
- 購入メモ `notes` はカードごとで全デッキ共通
- 保存先は `localStorage`（キー `ygo.data.v1`）。変更のたびに全体を書く（数十KB程度）
- 書き出しは同じ形の JSON。読み込みは `version` と各フィールドの型を検証し、通らなければ拒否する

### 5. 画面の操作

- デッキ編集は上にデッキ（メイン・エクストラ・候補）、下に検索欄の縦並び（スマホ幅）。PC幅ではマスターデュエルと同じ左右並び
- タイルのタップ＝未所持の切り替え、長押し（約0.5秒）＝メニュー（1枚抜く・移す・表紙にする・購入メモ・公式DB・カードラッシュ）
- 検索欄の上に追加先の切り替え（デッキ / 候補）
- 枠の色: 通常＝黄、効果＝橙、儀式＝青、融合＝紫、シンクロ＝白、エクシーズ＝黒、リンク＝紺、魔法＝緑、罠＝赤紫、ペンデュラムは下半分を緑にする
- カードラッシュ: `https://www.cardrush.jp/product-list?keyword=<名前をURLエンコード>`（検索結果に価格が出ることを確認済み）
- 公式DB: `https://www.db.yugioh-card.com/yugiohdb/card_search.action?ope=2&cid=<cid>`

### 6. 絵の暗号化

- 元画像は YGOPRODeck の切り抜きイラスト（`cards_cropped/<パスワード番号>.jpg`）。取得は1秒に5件以下、取得済みはローカルのキャッシュ（gitignore）から再利用
- 幅200pxの WebP に縮め、AES-GCM 256 で暗号化して `art/<cid>.bin`（`iv(12バイト) | 暗号文`）に置く。約14,000枚 × 数KB で、合計100MB前後の見込み
- 鍵は合言葉から PBKDF2-HMAC-SHA256（30万回）で作る。塩は全ファイル共通で `art/meta.json` に置く。1枚ごとに塩を変えると、表示のたびに30万回の計算が要るため
- `art/meta.json` には、決まった文字列を暗号化した確認用の値を入れ、合言葉が正しいかをファイルを取りに行く前に判定する
- `art/index.json` に絵のある `cid` の一覧を置き、無いカードには取りに行かない
- 画面は復号した画像を IndexedDB に `cid` と塩の組で保存する。合言葉を変えて全部作り直したとき（塩も変わる）は、古い保存分を使わない
- 合言葉は PC 側 `.env` の `YGO_ART_PASSPHRASE`（gitignore）と GitHub の Secrets に置く。画面側は `localStorage` の `ygo.pass.v1` に置き、書き出しには含めない

- 代替案: 複数枚を1ファイルにまとめる → デッキの絵はばらばらの位置にあり、1デッキを開くのに大半のまとまりを取ることになるので採らない
- 代替案: 筋トレチェッカーの KCZ2 形式（ファイルごとの塩、4MB区切り）→ 数KBの画像には過剰で、ファイルごとの塩は上記の理由で重い

### 7. 定期更新と公開

- GitHub Actions を週1回（と手動実行）で動かし、`build_cards.py` → `build_art.py`（新しい `cid` の分だけ）→ 変化があれば main に commit / push
- Pages は main のルートから配信する。Actions の push で自動的に反映される
- 初回の絵の一括作成は、時間がかかるのでローカルで実行してから push する

## Risks / Trade-offs

- [公式の一覧ページの作りが変わる] → 区切りが読めなければ更新を失敗させて前回のデータを残す。取得は週1回1ページだけにする
- [改定の適用日より前に一覧が切り替わる・後に切り替わる] → 公式DBの表示に従う。画面にデータの更新日を出す
- [ygocdb の API は v0 で、項目が予告なく変わりうる] → 変換は保存した見本データでテストし、本番で項目が欠けたら更新を失敗させて前回のデータを残す
- [ブラウザのデータ削除で利用者のデータが消える] → 書き出し・読み込みを設定画面の目立つ位置に置く
- [合言葉を渡した相手は絵を見られる] → 見られる範囲は合言葉の配り方で決まる。漏れたときは合言葉を変えて全部作り直す（手動実行の Actions で行う）
- [カードの絵の著作権] → 公開リポジトリには暗号化した状態でのみ置く。法的な扱いが変わるわけではない
- [iPhone の Safari での PBKDF2 30万回の時間] → 未計測。実機で1秒を大きく超えるなら回数を見直す
